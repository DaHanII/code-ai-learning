## 1. 为什么学 Ossie，以及学到哪里

Apache Ossie（孵化中，原名 Open Semantic Interchange）主要定义跨 BI、分析与 AI 工具交换语义模型的公共格式。它用 JSON/YAML 表达数据集、字段、关系、指标和 AI 上下文；模型转换器另在 apache/ossie-converters 仓库。

**适合用它学习统一业务语义、指标定义和模型互通；系统学习数据建模时，以业务与维度建模为主线，用 Ossie 表达并检验设计结果。** 阅读顺序是业务问题 → 粒度与关系 → 事实和维度 → 指标合同 → Ossie 表达 → SQL 验证。

项目依据：[README](https://github.com/apache/ossie)、[核心规范](https://github.com/apache/ossie/blob/a498fce5455dcc209605cdbb30b21e47068ff15e/core-spec/spec.md)、[转换器](https://github.com/apache/ossie-converters)。

## 2. 分层知识地图

| 层次 | 必须回答的问题 | 核心概念 | 学习产出 |
| --- | --- | --- | --- |
| 业务与概念模型 | 谁参与，发生什么，状态如何变化？ | 业务过程、实体、事件、关系、术语边界 | 业务流程图、概念关系图、术语表 |
| 逻辑模型 | 一行代表什么，怎样唯一标识，什么关系会放大行数？ | 粒度、自然键/代理键、基数、函数依赖、规范化取舍 | 逻辑关系图、主键与关系约束 |
| 维度模型 | 如何支持分析，如何保留历史？ | 星型模型、三类事实表、一致性维度、角色扮演维、SCD | 总线矩阵、事实/维度清单、历史处理规则 |
| 指标与语义模型 | 业务术语如何映射到稳定计算口径？ | 度量与指标、聚合、过滤、时间、去重、维度可用范围 | 指标合同、Ossie 模型、业务同义词 |
| 物理与加工实现 | 如何把逻辑模型落成可维护的数据表？ | 数仓分层、分区、主键更新、CDC、迟到、幂等、性能 | DDL、加工 SQL、更新和补数方案 |
| 验证与治理 | 如何发现口径错误，如何安全演进？ | 对账、质量约束、血缘、负责人、版本、兼容性 | 样例数据、断言 SQL、变更记录 |

逻辑关系设计与分析模型的目标不同。先理解实体约束，再解释为什么为分析采用星型结构；物理布局与湖表主键设计可回到 Paimon/Flink 主线继续深入。

## 3. 维度建模必须掌握的内容

以 [Kimball 官方技术目录](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/)作为知识索引，按下面顺序总结，每条配一个自己的业务例子：

1. 四步设计：选择业务过程 → 声明粒度 → 确定维度 → 确定事实。
2. 事实表：事务事实表、周期快照、累积快照；解释为什么支付事件、每日余额、订单履约过程需要不同粒度。
3. 可加性：金额通常能在约定范围内相加；余额不能直接跨日期相加；比率应重新汇总分子和分母，避免平均百分比。
4. 维度：自然键与代理键、一致性维度、退化维、日期维和角色扮演维。
5. 历史：SCD Type 1 覆盖与 Type 2 增行；明确“按交易当时属性”还是“按当前属性”分析。
6. 多事实分析：支付和退款先各自聚合到共同粒度，再关联；避免直接把两侧明细连在一起后求和。
7. 工程边界：迟到事实、退款回溯、CDC 重放、去重与补数，怎样改变历史报表。

## 4. 指标合同：先写口径，再写表达式

每个指标至少记录：

| 项目 | 需要写清的内容 |
| --- | --- |
| 名称和业务目的 | 同名指标是否存在多个定义，服务什么决策 |
| 粒度与数据来源 | 输入粒度、输出粒度、源表/字段、关联路径 |
| 公式 | 分子、分母、去重键、单位、精度与舍入 |
| 纳入范围 | 成功/失败/取消状态、测试数据、退款是否计入 |
| 时间 | 事件时间或入仓时间、时区、统计窗口、截止时点 |
| 维度与历史 | 可用维度，历史属性或当前属性，允许怎样汇总 |
| 边界行为 | 空值、零分母、负值、重复事件、迟到与补数 |
| 验证与维护 | 期望结果、对账 SQL、负责人、版本与生效时间 |

例如“客单价”不能只写 AVG(amount)：先明确是订单金额、成功支付金额还是净支付金额，分母是全部订单还是成功支付订单；不同口径应分别命名。

## 5. Ossie 概念与建模结果的映射

| Ossie 元素 | 对应的设计结果 | 需要额外验证的事项 |
| --- | --- | --- |
| datasets / source | 逻辑数据集与物理表、视图或查询的映射 | 源数据是否真的符合声明粒度 |
| primary_key / unique_keys | 数据集唯一标识与候选键 | 声明唯一不代表真实数据没有重复 |
| fields / datatype / dimension | 字段、逻辑类型与分析维度角色 | 时间字段的值类型与时间角色需分别理解 |
| relationships | 数据集之间的连接定义 | 关系是否会放大行数、漏掉数据，需用数据验证 |
| datasets[].metrics / 根级 metrics | 单数据集和跨数据集指标 | 聚合粒度与过滤范围是否符合合同 |
| description / ai_context | 业务定义、同义词、使用说明与示例问题 | 描述准确性及 AI 是否真正使用这些信息 |
| custom_extensions | 核心规范以外的厂商信息 | 哪些消费者能理解，往返转换是否保留 |

**锁定版本的重要限制**：核心规范 0.2.0.dev0 中，指标表达式引用已声明的数据集字段，不能直接引用其他指标，也不能绕过字段声明直接引用 source 列。设计派生指标时，先形成业务依赖图，再按该版本允许的表达式或预计算字段实现，不套用其他语义层的语法。

Ossie 校验器会检查 Schema、名字、引用和相应 SQL 语法等问题；**校验通过不等于业务口径正确、数据主键唯一或查询结果正确**。仍需使用独立 SQL 和预期结果对账。

依据：[指标与名称解析规范](https://github.com/apache/ossie/blob/a498fce5455dcc209605cdbb30b21e47068ff15e/core-spec/spec.md)、[验证脚本](https://github.com/apache/ossie/blob/a498fce5455dcc209605cdbb30b21e47068ff15e/validation/validate.py)。

## 6. 用同一个案例贯穿学习

选择“订单—订单明细—支付—退款—客户—商品”。默认用合成数据练习，真实业务问题另在 backlog 中登记来源。

| 对象 | 示例粒度 | 需要研究的设计问题 |
| --- | --- | --- |
| 订单 | 一行一订单 | 下单时间、订单状态、取消订单是否纳入 |
| 订单明细 | 一行一订单行 | 商品维度；订单级金额怎样分摊，是否具备可靠依据 |
| 支付 | 一行一支付事件 | 多次支付、成功状态、重复回调、支付时间 |
| 退款 | 一行一退款事件 | 多次退款、跨日退款、退款归因与截止时间 |
| 客户维度 | 一行一客户版本 | 业务键、代理键、有效时间区间 |
| 商品维度 | 一行一商品版本或当前商品 | 历史类目变化按何种口径分析 |

至少区分两种时间视角：订单批次截至某时点的累计净支付，与某个自然日的支付减退款现金流。它们回答不同问题，结果不应强行对齐。

## 7. 与现有源码主线的联系

- Datus：研究业务语义如何进入检索和上下文，比较只有表结构与增加指标定义后的查询结果。是否支持 Ossie 原生导入需要核对锁定版本，不能预设。
- Paimon：研究主键更新、changelog、snapshot 怎样支撑模型的状态与历史需求；存储主键与业务实体标识需要分别定义。
- Flink：研究事件时间、watermark、去重与迟到修正怎样影响指标结果。
- Spark：用批处理对账 SQL 复核指标，学习关联与聚合计划。
