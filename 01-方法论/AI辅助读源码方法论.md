# AI 辅助读源码方法论

> 专题题库：旧周次与大型练习仅供选题；当前以[源码 + 应用实践统一路线](../02-路线图/00-总路线图.md)的单元、运行和源码验收为准，不叠加任务。

> 适用：Datus（Python / Agent 框架）、Paimon（Java / 存储）、Flink（Java / 分布式运行时）、Spark（Scala / 查询引擎）。
> 前提：你已学过 LangChain / LangGraph 的基础用法，统一路线的单元 1–3 会通过运行、追源码和实验补齐框架机制。所以下面的方法从「大仓库怎么读」讲起，不再重复框架入门。

## 一、先说结论：AI 的三件正确用法和三种错误用法

**正确用法**

- **导航**：仓库几万行，AI 帮你定位「这个功能在哪个模块、哪个类、哪一行」，你只读该读的部分。
- **解释**：对一个方法/字段，AI 补上背景（设计约束、历史原因、上下游协议），把你从「语法看懂了但不知道为什么」里拉出来。
- **出题与找错**：让 AI 根据代码出题考你、检查你的笔记结论、设计最小复现实验。这是收益最高、也最容易被忽略的用法。

**错误用法**

- 让它「总结一下 Flink 的架构」——会得到一篇和官网博客没区别、且可能过期的东西。
- 一次丢一个大目录让它「讲讲」——上下文被稀释，回答又长又虚。
- 相信它给的类名和方法签名——大模型对老版本代码记忆很深，对新版本改动经常一本正经地编。

一句话：**AI 是陪你读源码的资深同事，不是替你读源码的替身。**

## 二、四层读法（每个仓库都按这个节奏走）

### L0 地图层：先知道「有什么」，不碰细节（0.5-1 天）

目标产出：一页纸架构图 + 模块职责表 + 一条「最小可运行路径」。

做法：
1. 只读 `README`、`docs/` 的 Overview、`pom.xml` / `pyproject.toml` 的模块划分。
2. 用提示词 P1 让 AI 生成仓库地图，**要求每个结论给出 `路径:行号`**，然后自己抽查 3 处。
3. 跑通官方 quickstart。跑不通就先解决环境，这一步没过，后面全是纸上谈兵。

判断标准：你能不看资料说出「这个项目由哪 5 个模块组成，数据从哪进、从哪出」。

### L1 骨架层：只追一条主链路（每个仓库 3-5 天）

目标产出：一张端到端调用链时序图，从用户入口到最终落点。

做法：
1. 选一条**最短、最常走**的链路。Flink 选「提交一个 WordCount 作业」，Paimon 选「Flink 写入一张主键表并提交 snapshot」，Datus 选「用户问一句 → 返回一个 SQL 答案」。
2. 用 P2 逐跳追问：每一跳的「输入是什么、谁调用谁、状态存在哪、失败会怎样」。
3. 每确认一跳，就把 `类名 + 方法名 + 文件:行号` 记进笔记，形成链条。**链条上的每一环都必须是你亲自打开文件看过的。**

判断标准：能对着白板从入口画到落点，中间不断线。

### L2 机制层：按问题深挖（每个项目挑 4-6 个专题）

骨架是一条线，机制是一个个「点」。每个点用一个**问题卡片**驱动，卡片结构固定：

```
问题：checkpoint 时如果某个算子一直不来 barrier 会怎样？
为什么问：线上遇到过 checkpoint 超时
读哪里：CheckpointBarrierHandler / CheckpointCoordinator 的超时逻辑
验收：能说出超时后作业的行为（失败？降级？）以及对应配置项
```

L2 的读法是**以状态变化为中心**，不是以文件为中心。读一个机制时固定问五个问题：

1. 输入是什么（消息、配置、外部事件）？
2. 内部有哪些状态（内存结构、文件、元数据）？
3. 状态怎么变（正常路径）？
4. 边界和异常怎么处理（超时、并发、重启、部分失败）？
5. 对外暴露什么（配置项、指标、日志、异常类型）？

这五个问题问完，一个机制才算读透。AI 在这里主要帮你做第 3、4 步——异常路径最容易被自己漏掉。

### L3 验证层：输出即检验（每篇笔记 0.5 天）

三种验证手段，按成本从低到高：

- **复述**：合上代码，用自己的话讲一遍链路，然后让 AI 挑错（P9）。讲不顺的地方就是没读懂的地方。
- **出题**：让 AI 基于代码出 5 道题（P5），答不上来的回头补。
- **实验**：写最小 demo 或加日志/断点实际跑一遍（P8）。涉及分布式状态的（checkpoint、snapshot、shuffle）尽量做，因为这类机制光看代码必然有理解偏差。

判断标准：你的笔记能让一个没读过这个项目的同事看懂，并且他能顺着笔记自己找到代码。

## 三、防幻觉纪律（硬性规则）

1. **版本锚定。** 进仓库第一件事：`git checkout` 到你要研究的 tag（如 `release-1.20`、`paimon-1.2`），并在每次对话开头告诉 AI「当前版本是 X」。训练数据里的老版本会系统地骗你。
2. **行号即证据。** 凡是「XX 在这里做的」结论，必须带 `文件:行号`。AI 给不出行号的结论，一律标 `[未验证]`。
3. **一次一问。** 一条链路、一个机制、一个类。跨模块的大问题拆成小问题串行问。
4. **交叉验证。** AI 说法 → 官方文档 → 代码注释 → 实际运行，至少对上两项才写进笔记。四者冲突时以代码和运行结果为准。
5. **警惕流畅。** 回答越顺畅、越像教科书，越要抽查。真正的源码细节往往是反直觉的。
6. **区分「设计意图」和「实现现状」。** AI 很擅长讲设计意图（因为文档里写了），但实现里可能有 workaround、兼容代码、TODO。读代码时专门留意 `TODO`、`FIXME`、`@Deprecated`、奇怪的 if 分支，那里往往藏着真实世界的约束。

## 四、环境准备（一次性，约半天）

**通用**

- 每个仓库单独克隆，建一个学习分支：`git checkout -b study/<tag>`，不要在你的工作分支上读。
- 在仓库根目录让 AI 生成 `CLAUDE.md`（或 `.cursor/rules`），内容包括：模块地图、入口类、构建命令、代码风格约定。**这份文件是后续所有会话的上下文底座**，比每次重新解释仓库高效得多。
- 笔记与代码分离：代码在 D 盘源码目录，笔记在本目录 `04-笔记/`，笔记里只放 `文件:行号` 和链接。

**Java 系（Flink / Paimon / Spark）**

- JDK 11/17（按项目要求）、Maven 3.8+，先跑 `mvn -DskipTests install` 确认能编译。编译不过的项目读起来会非常痛苦，因为无法跳转和调试。
- IDE 打开后等索引建完再开始；用 IDEA 的「Find Usages」和「Call Hierarchy」配合 AI 使用——AI 负责告诉你「去哪找」，IDE 负责「精确地找」。
- 装 Mermaid 插件，笔记里的时序图直接在 IDE 里预览。

**Python 系（Datus）**

- `uv` 或 `venv` 建独立环境，`pip install -e .` 可编辑安装，方便打断点。
- 用 `duckdb` 做本地数据源跑 demo，不要一上来接生产库。

**AI 工具的分工建议**

- **Claude Code / Cursor 在仓库内**：负责搜索、跳转、追链路、改代码做实验。能直接 grep 和读文件，幻觉最少。
- **网页版对话**：负责概念解释、对比阅读、帮你审笔记。适合贴片段，不适合贴大目录。
- **本地 grep 仍然是第一手段**：`rg "class CheckpointCoordinator"` 比问 AI 快且准。AI 的价值在「grep 之后怎么串起来」。

## 五、学习单元节奏（问题驱动版）

一个单元完成一个循环，复杂机制可以拆成多次；至少留下一篇有应用与源码证据的笔记：

| 时间 | 动作 | 产出 |
| --- | --- | --- |
| 开始 | 从 backlog 挑一个可复现问题，写出输入与预测 | 问题卡片 |
| 运行与追踪 | 跑最小例子，沿实际链路读 L1/L2 源码，每跳记 `文件:行号` | 运行记录 + 链路图 |
| 边界实验 | 改一个输入或条件，核对状态与异常分支 | 预期/实际对照 |
| 完成 | L3：复述、出题并写明对应用设计的影响 | 一篇成文笔记 |
| 收尾 | 更新 backlog：新问题入库，已解决的标证据和结论 | backlog 更新 |

每完成一个阶段做一次**横向对比**（1 小时）：比如「Paimon 的 snapshot 提交 vs Flink 的 checkpoint 完成」「Datus 的 agent loop vs LangGraph 的 StateGraph」。对比是检验理解最狠的方式，也是最能产出洞见的时刻。

## 六、读不同项目的差异化策略

- **Python 项目（Datus）**：代码量小、动态性强，重点不是读实现细节，而是**读出架构决策**——它为什么不用 LangGraph、context 怎么组织、工具怎么注册。读的时候多问「如果是我会怎么设计」。
- **存储格式（Paimon）**：核心是**元数据与文件布局**。先把「表 → snapshot → manifest → data file」的层次在纸上画清楚，再读代码。存储项目的代码是围绕这几个数据结构的 CRUD，看懂结构就懂了一半。
- **分布式运行时（Flink）**：最难的是**跨进程、跨线程的状态**。读的时候始终问「这段代码运行在 JobManager 还是 TaskManager？哪个线程？」。建议先读 `flink-runtime` 的部署与调度，再读 `flink-streaming-java` 的算子执行。
- **查询引擎（Spark）**：核心是**树变换**。Catalyst 的一切都是「Tree + Rule」，读的时候把每条 Rule 当成一个 `Tree → Tree` 的函数，重点看 rule 的匹配条件和幂等性。不要试图读完所有 rule，挑 5 条最常用的。

## 七、常见坑

- **一上来读最难的模块。** Flink 直接读 NetworkStack、Spark 直接读 Tungsten，三天就会放弃。永远从最短链路开始。
- **只读不跑。** 分布式系统的代码，不跑一遍几乎必然理解错。至少把 demo 跑起来加日志。
- **笔记写成代码摘抄。** 抄代码没有价值，笔记要写「为什么」和「链路」，代码只留 `文件:行号`。
- **让 AI 一次读整个文件。** 大文件（几千行的 Operator）要按方法读，让 AI 只解释你圈出的那一段。
- **忽略配置项和指标。** 配置项是设计意图的索引（有哪些开关说明有哪些路径），指标是运行时行为的索引。读机制时顺手记下相关配置和 metric 名，回填工作特别有用。
