# 提示词库

用法：复制后把 `<尖括号>` 里的内容替换掉。所有提示词都默认带了「版本锚定 + 行号强制 + 不确定就说不确定」的约束，**不要删掉这几条**，它们是防幻觉的核心。

通用前置句（建议每段对话开头都带上）：

```
当前仓库：<repo>，版本：<tag/commit>。回答必须遵守：
1. 每个结论附 `文件路径:行号`；
2. 找不到依据时明确写「未在代码中找到」，不要猜；
3. 不确定的地方标注「推测」并说明理由；
4. 只回答我问的这一条链路，不要展开无关模块。
```

---

## P1 仓库地图（L0，每个新仓库跑一次）

```
你是我的源码阅读向导。请先只读 README、docs 的 overview 和构建文件，产出：
1. 模块清单表格：模块名 | 职责（一句话）| 主要目录 | 大概行数规模；
2. 一张 Mermaid 架构图，画出模块间依赖和数据流；
3. 「最小可运行路径」：从用户入口（CLI/API）到最核心逻辑的一条最短调用链，列出每一步的类和方法；
4. 列出 3 个最适合初读者的入口文件，并说明理由。
要求：每条结论给 `文件:行号`；不确定的地方标「推测」。最后告诉我，要理解这个项目，哪 3 个概念必须先搞懂。
```

产出直接存成仓库根目录的 `CLAUDE.md`：

```
把上面的结果整理成一份 CLAUDE.md，包含：项目定位、模块地图、核心抽象（5 个以内）、
构建与运行命令、代码风格约定、阅读入口。要简洁，作为后续所有对话的上下文底座。
```

## P2 调用链追踪（L1，最常用）

```
入口是 <类名.方法名>（文件:行号）。请追踪它在「<具体场景>」下的执行路径，要求：
1. 每一跳给出：调用方 → 被调方（类.方法）、文件:行号、这一跳做了什么、输入输出是什么；
2. 遇到接口/抽象类时，指出运行时实际的实现类是哪个，并说明你是怎么判断的；
3. 遇到多线程/异步（线程池、消息队列、RPC），单独标注「切换到了哪个线程/进程」；
4. 输出一张 Mermaid 时序图。
只追到 <你关心的落点，如：数据写入文件> 为止，不要继续往下展开。
```

变体：**反向追踪**

```
<某现象/字段/表> 是从哪里来的？请反向追踪它的写入点和赋值点，直到最上游的来源。
列出所有写入点，并说明哪个是主路径、哪些是兼容/修复路径。
```

## P3 机制解释（L2，配合五个问题）

```
请解释 <机制名> 的完整生命周期，按以下结构回答：
1. 触发条件：什么情况下会进入这个流程；
2. 状态：涉及哪些内存结构和持久化数据，分别存在哪；
3. 正常路径：分步骤描述，每步给 `文件:行号`；
4. 异常路径：超时、失败、并发冲突、重启时分别怎么处理，给 `文件:行号`；
5. 对外接口：相关配置项、指标名、日志关键字、抛出的异常类型。
最后指出：这段代码里有没有 TODO / FIXME / 特殊兼容分支？它们说明了什么约束？
```

## P4 对比阅读（每完成一个阶段）

```
对比 <项目A的机制X> 和 <项目B的机制Y>，回答：
1. 两者要解决的问题是否相同？如果不同，各自真正的约束是什么？
2. 在数据结构/状态模型上的差异；
3. 在失败恢复上的差异；
4. 各自的取舍（性能/复杂度/一致性）分别偏向哪边；
5. 如果我所在的团队同时用两者，最容易踩的坑是什么？
每条结论给出两边的 `文件:行号` 作为依据。不要为了对称而强行类比。
```

可用对比清单：Paimon snapshot vs Flink checkpoint；Paimon LSM vs RocksDB；Datus agent loop vs LangGraph StateGraph；Flink 两阶段提交 vs Paimon 的 commit；Spark AQE vs Flink 动态调整并行度。

## P5 出题自测（L3）

```
基于 <机制名> 的实现，出 6 道题考我，难度递进：
2 道概念题（考状态模型）、2 道链路题（考调用顺序）、2 道故障题（给一个线上现象，问根因在代码哪一段）。
先只给题目，我答完再给评分和解析。解析必须引用 `文件:行号`。
```

## P6 生成图表

```
把 <链路/机制> 画成 Mermaid 时序图（参与者用真实类名），要求：
- 标注线程/进程边界（用 Note）；
- 标注状态变化点；
- 只画主路径，异常路径用 Note 说明。
如果信息不足以画完整，先列出缺失的信息点，不要编造参与者。
```

（状态机用 `stateDiagram-v2`，数据结构层次用 `classDiagram` 或缩进列表。）

## P7 代码考古（理解「为什么」的利器）

```
这段代码 <文件:行号> 看起来很奇怪 / 是 workaround。请：
1. 用 git log -L 和 git blame 找到引入它的 commit 和 PR；
2. 结合 commit message、PR 描述、关联 issue，解释当时要解决什么问题；
3. 说明今天的代码是否还受那个约束限制。
如果查不到历史，明确说「无历史记录」，不要用设计意图代替历史事实。
```

## P8 最小实验设计

```
我想验证 <机制> 的实际行为。请设计一个最小实验：
1. 环境：需要哪些依赖、用哪个版本、用什么数据源（优先 duckdb/本地文件）；
2. 代码：不超过 50 行的 demo，能触发这个机制；
3. 观察点：加哪些日志/断点/指标，期望看到什么，如果看到 X 说明理解正确；
4. 反例：怎样构造一个让机制走异常路径的输入。
给出完整可运行的代码，并说明每一步验证的是哪个假设。
```

## P9 审我的笔记（L3，写完必做）

```
以下是我的源码笔记。请只做三件事：
1. 找出与代码不符或缺少 `文件:行号` 支撑的结论；
2. 找出我漏掉的关键分支（尤其是异常路径和并发场景）；
3. 指出我写得含糊、别人看不懂的句子。
不要重写我的笔记，只列问题清单。
笔记：<粘贴>
```

## P10 版本差异阅读（升级/回填工作时用）

```
我在读 <项目> 的 <旧版本>，现在要升级到 <新版本>。请对比这两个版本在 <模块/机制> 上的差异：
1. 新增/删除/重命名的核心类；
2. 行为变化（默认值、协议、元数据格式）；
3. 兼容性影响；
4. 建议我优先读的 3 个新文件。
以两个版本的实际代码为准，不要凭记忆回答。
```

## P11 把源码结论翻译成工作语言

```
基于以上源码结论，帮我写一段给团队看的话：
1. 这个机制在我们的 <Flink/Paimon/Spark 集群> 上意味着什么；
2. 我们应该关注哪几个配置项和指标；
3. 出现 <某现象> 时，排查顺序是什么（按代码里的实际路径）。
用工程师能直接执行的语言，不要复述源码。
```

---

## 提示词使用纪律

- **P1 每个仓库只跑一次**，结果固化成 `CLAUDE.md`；之后每次会话让它先读这份文件。
- **P2 是主力**，一周里 70% 的对话应该是 P2 和 P3。
- **P5、P9 不要省**，它们是「以为读懂了」和「真读懂了」的分界线。
- 同一段对话不要超过 15 轮。话题切换就开新会话，避免上下文污染。
- AI 回答完，先做一件事：抽查它给的第一个 `文件:行号`。对不上，整段作废。
