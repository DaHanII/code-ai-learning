## 本周要回答的主问题

用户说一句“查 2026-10-04 各渠道日活”，**模型究竟返回了什么，程序凭什么接受或拒绝它？** 遇到歧义、非法指标、超时或流式中断，应用应留下什么状态，才不会把半截输出或错误文本当成答案？

本周只完成“输入 → 模型响应 → 参数解析 → 程序校验”的链路；可以读取固定 JSON 样例来校验指标 ID 和训练时钟，但不接工具、RAG、数据库或 Agent 循环。数值查询和分区可用性留到下一单元。

## 3. 思考题（先写预测，跑完再修正）

1. 课程 `api_requests.py` 的请求体、响应体各有哪些字段？请求成功返回 HTTP 响应，是否就等于已经拿到可用答案？你会在哪里检查状态码、结束原因与用量？
2. System、Human、AI 消息各承担什么职责？如果把系统规则、用户问题和历史对话拼成一条字符串，后续哪几种边界会难以检查？
3. `llm_client.py` 的 `chat()` 中既有 `yield` 又有 `return`。调用者在 `stream=False` 时实际拿到什么类型？用 `for chunk in ...` 能否得到 `return` 的文本？先预测，再用一个不联网的小实验验证。
4. 课程 `llm_client.py` 捕获异常后把错误作为文本片段 `yield`；`chat_service.py` 又会累积片段。调用者怎样区分“模型回答”和“调用失败”？如果输出格式是普通文本，会出现什么风险？
5. 流式响应已经收到半个 JSON，但连接中断。界面可以展示已收到字符，业务流程何时才可以接收解析结果？完成标志应由哪一层产生？
6. 课程的 `3-prompt_json.py` 只要求模型“严格 JSON”；`chat_service.py` 的 `validate_json_output()` 主要检查可解析性。请分别举出“不是合法 JSON”“合法 JSON 但字段不符”“字段齐全但业务值非法”三个反例。为什么仅靠提示词或正则提取都不足以通过业务验收？
7. 给“昨天各渠道表现如何”加一个 Few-shot 示例，如果示例里默认查询日活，会怎样影响澄清行为？什么信息可以从固定训练时钟确定，什么仍必须追问？
8. 同一输入经原生请求/课程 SDK 封装/LangChain 调用时，哪些工作由封装完成，哪些仍应由你的应用负责？用实际源码位置说明，不按方法名猜测。

## 4. 实践题

### P1 · 复现并审查课程代码（不联网）

用假响应/假异常驱动课程的 `LLMClient.chat()` 和 `ChatService.validate_json_output()`；可以在自己的练习目录写最小复现，不改课程原件。

- 证明 `stream=False` 的返回行为，并记录调用者实际观察到的类型和内容。
- 模拟一次中途断流和一次调用异常：观察错误是否与普通内容走同一路径。
- 对 JSON 验证函数输入三类样例：纯合法 JSON、被说明文字包裹的 JSON、字段正确但 `metric` 为“收入”的 JSON。记录它返回的状态以及应用还需补的校验。
- 找出课程源码中的正常路径与失败路径各 2–3 个位置，并给出你会怎样修改返回契约的**设计草图**，本周不重写课程项目。

**交付**：一张“预测 → 实际 → 源码位置 → 改进判断”表。这里考的是读懂代码与发现边界，不以找出多少问题计分。

### P2 · 做一个可核验的参数抽取入口

在现有练习仓库或独立小文件中使用 LangChain ChatModel。输入是一句中文问题和服务端给定的训练时钟；输出字段为：

`intent, metric, dimensions, time_range, filters, missing_fields, status`

`status` 至少包含 `ready`、`needs_clarification`、`invalid`。允许的指标 ID 从固定样例 `metrics` 读取。先保存原始 AIMessage/原始文本，再解析 JSON 或结构化结果，最后由程序验证字段、指标枚举、日期顺序与缺失项。记录 `request_id`（本地生成即可）、模型/配置、耗时、结束状态及可获得的 usage；没有 usage 时记“未提供”，不要估造。断流不能进入后续解析或答案生成。

| 输入 | 必须检验的行为 |
| --- | --- |
| 查 2026-10-04 各渠道日活 | `metric=dau`、渠道维度、日期明确，程序可接受参数 |
| 昨天的日活是多少 | 训练时钟下解析为 2026-10-04 |
| 昨天各渠道表现如何 | 指标缺失，`needs_clarification`，不能默认日活 |
| 查 2026-10-04 各渠道收入 | “收入”不在允许指标中，澄清或拒绝，不能偷换为 `paid_amount` |
| 查 2026-10-04 至 2026-10-03 的日活 | 日期逆序由程序拒绝，即使模型输出是合法 JSON |
| 查 2026-10-05 日活 | 只能得到可解析参数；数据是否完整仍待核查，不能报 0 或编造人数 |

**交付**：Schema、调用与校验代码、六行输入/原始输出/解析结果/最终状态表。没有可用模型密钥时，用假模型完成控制流验证，并把真实抽取表现标为“未验证”。

### P3 · 四种调用结局与源码对照

给 P2 的调用入口注入“正常返回、鉴权失败、超时、流式中断”四种情况，不需要真实触发收费接口的故障。每种情况记录 `completed / failed / incomplete`、错误类型、耗时与可获得的 usage；原始异常不作为模型回答。追一次正常 `invoke` 或 `stream` 到 LangChain 核心源码，记录关键 3–5 跳；再对照课程 `LLMClient.chat()` 与自己入口的返回契约。

**交付**：四条可复现记录、一张三列对照表（课程实现 / LangChain 封装 / 自己的业务校验），以及一条“我原来以为 X，源码和运行显示 Y”的结论。

## 5. 本周过关标准与范围边界

同时满足以下四项即可进入下一个单元：

- 能现场解释一次调用从消息构造到程序接受/拒绝的每一步，分清模型输出、JSON 解析、Schema 和业务校验。
- P2 六个输入中，歧义会追问，非法指标和逆序日期由程序拦下；不会凭参数抽取给出实际指标数值。
- P3 四种结局可区分；中途断流标 `incomplete`，错误文本不被当成成功答复，缺失 usage 不编造。
- 笔记附课程源码与 LangChain 固定版本的亲自核对位置、一次预测被推翻的反例，以及一条对应用设计的影响。没有真实模型调用时明确标出验证范围。

**本周不做**：工具执行、检索/RAG、完整 Agent、数据库查询、多轮记忆、部署。课程 S03 及后续题目留到对应单元。练习的依赖缓存和运行记录放在 `D:\hy\codex\ai-source-learning\week1` 的子目录；最终笔记放在本项目 `04-笔记/`。
