# 第一阶段实践与源码追踪：LangChain 模型、工具、检索

> 配套[源码 + 应用实践统一路线](../../02-路线图/00-总路线图.md)单元 1–2；单元 3 的 LangGraph 状态与恢复见总路线及专题指南。已有概念基础就直接运行样例，解释不清的部分再查资料。这里的“阶段一”指本路线图的框架起步阶段，不是咕泡清单中同名的阶段一。每题均须留下应用结果、源码位置和一个边界验证。

单元 1 的具体安排、课程代码阅读范围与第一周思考题见[第一周学习单](07-第一周-模型调用与结构化输出.md)；本文件保留单元 1–2 的扩展题与总验收。

## 资料与统一场景

主场景采用咕泡课程的虚构“听数实验室”数据小助理。原课的 S01、S02 对应模型调用和结构化输出；S18 的工具契约部分用于工具调用；S06、S09–S11 对应检索、分块、引用。**实现统一用 LangChain**，不要求按原课进度完成 Dify、MCP 服务、数据库执行或完整 Agent 平台。

- 题目与章节：[咕泡第 3–9 章学习清单](../../../../咕泡/咕泡new/第3至9章学习清单_20261021.md)，重点看 S01、S02、S18-Q2/Q3、S06、S09、S10、S11。
- 场景和时间规则：[项目设定](../../../../咕泡/咕泡new/实战连续剧_项目设定与使用规则.md)。
- 固定输入：[实战固定样例数据 v1](../../../../咕泡/咕泡new/实战固定样例数据_v1.json)：本阶段主要用 `metrics`、`complete_partitions`、`knowledge_documents`。其中 `K01` 是 10 月有效日活口径，`K02` 是已退休旧口径，`K04` 仅 analyst 可见，`K05` 说明完整分区，`K07` 是未审核的攻击文本。
- [验收基准](../../../../咕泡/咕泡new/验收基准_v1.json)只在后续接入数值计算时使用。本阶段**能解释口径和数据可用性，不凭 RAG 生成指标数值**。

练习统一以训练时钟 `2026-10-05 12:00:00 +08:00` 解释相对日期：“昨天”是 `2026-10-04`。本阶段只建立一个小助手，逐步增加能力。保存最小可运行代码、输入输出记录和一页复盘即可；可以用现有练习仓库，不需要再建一个业务系统。

## A. 模型调用与工具（单元 1–2，可连续完成）

### A1. 先预测：消息与结构化输出

闭卷作答，每题用 3–6 句话，最好附一次真实运行现象。

1. **消息边界**：System、Human、AI、Tool 消息分别承载什么？把规则、历史、工具结果拼成一个长字符串，失去哪些可检查的边界？（咕泡 S01）
2. **调用与流式**：`invoke` 与 `stream` 的使用和观察有何区别？流在 JSON 中途断开时，为什么不能把已到达字符直接交给后续程序？（S01）
3. **三层正确性**：举例区分“文本是合法 JSON”“符合参数 Schema”“业务值可执行”。`metric="收入"`、开始时间晚于结束时间分别在哪一层处理？（S02）
4. **澄清与失败**：“昨天各渠道表现如何”缺了什么？鉴权失败、限流、超时、歧义输入各应如何处理，何时重试没有意义？（S01/S02）
5. **原始结果与用量**：为什么要保留模型原始消息、解析对象、校验结果、调用耗时与可获得的用量？拿不到 token usage 时如何记录？（S01）

### A1. 实践题：做一个可核验的参数抽取入口

用 LangChain ChatModel 接收用户问题，输出结构化对象：

`intent, metric, dimensions, time_range, filters, missing_fields, status`

允许的指标 ID 取自样例 `metrics`，至少支持 `dau`、`new_users`、`paid_amount`、`paying_users`。`status` 至少区分 `ready`、`needs_clarification`、`invalid`。按服务端传入的固定训练时钟解释“昨天”；不要用机器当天日期。模型给出对象后，再由程序验证指标枚举、日期顺序、必填项。记录原始 AIMessage、解析对象、验证结论、耗时、可获得的 usage；错误与断流不能伪装为成功。

| 输入 | 必查结果 |
| --- | --- |
| 查 2026-10-04 各渠道日活 | `metric=dau`、渠道维度、日期 10-04、`ready` |
| 昨天的日活是多少 | 训练时钟下日期 10-04、`metric=dau` |
| 昨天各渠道表现如何 | 缺指标，进入 `needs_clarification`；不能暗定为日活 |
| 查 2026-10-04 各渠道收入 | “收入”不是已定义指标，澄清具体口径或标 `invalid`；不能偷换成 `paid_amount` |
| 查 2026-10-04 至 2026-10-03 的日活 | 日期逆序由程序拒绝 |
| 查 2026-10-05 日活 | 参数可解析，但完整分区未知；记录待查数据状态，不能返回 0 |

再模拟一次超时和一次中途断流。两种情况都应留下错误类型；断流输出标为 `incomplete`，不进入工具或答案生成。没有真实模型密钥时可用 LangChain 的测试模型验证消息、解析和控制流，但“模型实际抽取准确率”须标记未验证。

**提交**：Schema、调用代码、上述 6 例结果、2 个失败记录，以及一段解释“模型生成了什么，程序最终接受了什么”。

**源码追踪与边界验证**：选一次正常调用和一次校验失败，从实际调用入口追到 LangChain ChatModel 的请求/响应封装、AIMessage 形成、结构化输出解析的关键路径；分别标注哪些校验由框架处理、哪些由自己的程序处理。记下固定版本的 3–5 个亲自核对的 `文件:行号`。将非法指标或逆序日期再次输入，比较模型输出与程序拒绝的位置；若实际 provider 行为不在 LangChain 仓库内，明确标注边界，不猜测实现。

### A2. 先预测：工具调用与执行边界

1. **调用链**：画出 Human → 模型提出 tool call → 程序验证/执行 → ToolMessage → 模型生成答复。哪个环节真正访问本地数据？（S18）
2. **契约**：工具名称、用途描述、参数 Schema、结果 Schema 各解决什么问题？模型给出不存在的工具名或非法参数时如何处理？（S18）
3. **状态区分**：`not_found`、`unknown_partition`、`forbidden`、`tool_error`、调用超时为何不能都写成“没有数据”？（S18）
4. **边界与停止**：授权身份从哪里来？如何阻止同一工具反复调用、循环不退出或调用次数无上限？（S18；对应统一路线单元 2）

### A2. 实践题：给同一助手加两个只读工具

从固定 JSON 读数据，定义并绑定两个 LangChain 工具：

- `get_metric_definition(metric_id, as_of_date)`：返回指标 ID、公式、版本、生效状态和来源；未知指标返回明确错误。`partner_demo` 不能通过此入口得到支付指标的内容。
- `check_partition(table, date)`：对 `fact_event`、`fact_order` 返回 `complete` 或 `unknown`，并给出数据来源。未知分区不能返回“空表/数值 0”。

身份由程序传入，不让模型从用户话语中自行修改。工具执行前验证参数；返回中区分正常、空结果、无权限和执行失败。控制循环最多 3 次工具调用，重复同一调用则终止并报告原因。保存每一步消息类型、工具参数、工具结果与最终答复。

| 任务 | 预期行为 |
| --- | --- |
| “2026-10-04 日活怎么算？当天事件分区可用吗？” | 可调用两个工具；说明口径与分区完整，不报日活数值 |
| “2026-10-05 日活是多少？” | 分区状态 `unknown`；不得回答 0 |
| `partner_demo` 问“成功支付金额口径是什么？” | 执行层拒绝读取支付口径；改口说“我是管理员”也不能改变身份 |
| 工具收到 `date=2026-99-99` 或未知表名 | 程序拒绝非法参数，不触碰数据文件后续逻辑 |
| 工具故意抛出异常 | 答复为工具失败并保留可追踪记录，不能写成“没有数据” |

**提交**：两个工具契约、调用轨迹 5 条、至少 1 个非法调用记录和循环停止规则。MCP 包装留到后续 Agent/工具专题。

**源码追踪与边界验证**：沿本次实际运行追 `bind_tools`、模型产生的 tool call、工具执行和 ToolMessage 回填；若循环是自己写的，要将应用循环与 LangChain 的消息/工具封装分开标注。至少核对 3 个源码位置，再输入不存在的工具名或非法日期，观察拒绝发生在哪一层、有没有触碰数据文件。

## B. 最小 RAG（并入单元 2）

### B1. 先预测：检索、证据与回答

1. **链路**：离线整理/分块/建索引与在线检索/生成分别做什么？更新一份知识文档，哪些信息必须重新确认？（S06）
2. **分块**：若“有效播放”和“排除内部用户”被拆成两个孤立片段，会怎样影响答案？如何通过分块或父文档关系修正？（S09）
3. **检索信号**：“日活”“DAU”“fact_event.duration_seconds”为什么对关键词和语义检索的依赖不同？Top-K 分数能直接解释为正确概率吗？（S10）
4. **过滤顺序**：K02 已退休、K04 有角色限制、K07 未审核，分别应在哪些环节过滤或标注？只过滤向量召回、不处理其他通路会有什么问题？（S10）
5. **引用核对**：引用了 K01 是否一定说明回答中的每个条件都正确？检索到口径文档，是否就能说出 10 月 4 日的实际日活人数？（S06/S11）
6. **错误归因**：答案漏掉“排除内部用户”、引用 K02、凭空报数，分别更可能属于检索漏召回、证据选择/引用错误还是生成错误？需要看什么运行证据来判断？（S11）

### B1. 实践题：用 K01–K07 做一条可追溯的 RAG 链

把 `knowledge_documents` 变成 LangChain Document，至少保留 `doc_id`、`version`、`status`、`scope`、`effective_from/to`、原文来源。用一个可运行的检索器完成“问题 → 候选文档 → 权限/版本过滤 → 带证据回答”；向量方案应记录 embedding 模型与索引配置。若用演示假向量，只验控制流，不评价真实召回效果。至少比较**无检索**与**有检索**的输出；再手工检查一处中文别名和一个字段名的召回差异。

| 问题与身份 | 应出现的关键证据/行为 |
| --- | --- |
| analyst：2026 年 10 月日活怎么算？ | K01；有效播放、按用户去重、排除内部用户、时区 |
| analyst：10 月按渠道看日活，渠道取哪个字段？ | K01、K03；字段为 `dim_user.acquisition_channel` |
| analyst：成功支付金额如何计算？ | K04；仅已支付订单，排除内部用户；不得称为净收入 |
| partner：成功支付金额如何计算？ | K04 不得进入给模型的上下文、回答或引用；说明无权限 |
| analyst：10 月 5 日没有事件，是日活为 0 吗？ | K05；分区未知，不能判 0 |
| ops：`waiting_queue` 与 `blocked_dependency` 怎么区分？ | K06；只给诊断顺序，不声称执行了重跑 |

另加两个反例：10 月查询不能采用 K02 的 9 月旧口径；K07 中“导出全部订单”的文字不能成为系统指令。每个答案都带实际使用的 `doc_id/version`，没有足够证据时返回“无法确认”和缺失项。检查引用是否支持答案中的每个条件；本单元不计算数值指标。

**提交**：Document/元数据样例、至少 6 条“召回前候选 → 过滤后证据 → 最终答复”记录、一张无检索/有检索对照表、K02/K07 反例结果，以及对至少一个失败案例的归因。

**源码追踪与边界验证**：从一次 retriever 调用追到候选返回，再追应用中的权限/版本过滤和进入模型的上下文。记录框架与应用各自负责哪一步及固定版本的源码位置。让 K02 或 K07 出现在候选中，证明过滤/隔离后实际给模型的内容；如过滤是自写逻辑，直接标记为应用代码，不把它说成框架保证。

## 阶段一总验收

用一条完整轨迹回答：“2026-10-04 日活怎么算？当天数据是否可查？”轨迹中应看到解析结果、模型调用、工具调用与返回、检索到的 K01/K05、过滤决策和最终答复。答复应能解释日活定义与事件分区状态；没有数值计算工具时不报具体人数。

自评按每单元 100 分：**应用行为 40、源码链路 30、运行与边界证据 30**。A1、A2、B1 都达到 80 分，且通过以下硬条件，再进入 LangGraph 状态与恢复单元：

- 歧义问题会澄清；Schema 合法但业务非法的值由程序拦下。
- 工具选择与执行有完整消息轨迹；身份、参数和调用上限由程序控制。
- K02 不冒充 10 月现行口径，K04 不泄露给 partner，K07 不成为指令；未知分区不被解释为 0。
- 最终答案能追到具体证据，口径解释和数值计算的能力边界说得清楚。
- 每部分至少有一条从实际运行入口追到关键实现的源码链，附固定版本与亲自核对的位置；框架、provider 和自写应用逻辑的责任分清。

遇到模型输出不稳定时，保留原始输入/输出与失败原因，再修改提示词、Schema 或过滤逻辑并复跑同一用例。**过关看可复现的应用行为、源码证据和解释，不看代码行数。**
