## 1. 业务边界和指标合同

1. 选择订单、订单明细、支付事件、退款事件、客户、商品；逐个写“一行代表什么”，不能只列字段。
2. 对每个关系写出两端是否唯一、是否允许缺失、会不会增加行数。
3. 完成至少 5 个指标合同：成功支付金额、成功退款金额、净支付金额、成功支付订单数、每成功支付订单净额。模板见知识框架。
4. 写清订单批次、截止时点、支付/退款事件日期、时区、状态、去重键和零分母策略。
5. 讨论商品维度：支付只有订单级金额时，不能直接声称可按商品分析；需要先定义并验证分摊规则。

闭卷问题：订单金额、支付金额、净支付金额何时不同？支付事实的主键为什么通常不是 order_id？“客户”与“客户的某个历史版本”有什么区别？

## 2. 最小案例、标准答案与边界验证

基础案例全部金额单位为元、统一用 DECIMAL；时区 Asia/Shanghai。订单 A/B/C 均在 2026-10-01 创建，订单批次取当天；截止时点是 2026-10-03 00:00:00（不含）。只纳入成功支付和成功退款，所有事件均有独立 ID。

| 订单 | 订单状态 | 10 月 1 日成功支付 | 10 月 2 日成功退款 |
| --- | --- | --- | --- |
| A | 已支付 | P1=60，P2=40 | R1=10，R2=20 |
| B | 已支付 | P3=50 | 无 |
| C | 已取消 | 无 | 无 |

标准答案：截至截止时点，成功支付金额 150，成功退款金额 30，净支付金额 120，成功支付订单数 2，每成功支付订单净额 60。退款金额率 30/150=20%；有退款的已支付订单占比 1/2=50%，两者不能混用。

对比错误路径：A 的 2 条支付关联 2 条退款产生 4 行，支付被算成 200、退款被算成 60。正确路径是按订单分别汇总支付与退款后再关联；保留订单 B，退款额补 0。C 不进入成功支付订单数的分母。

时间口径对比：按事件日计算现金流净额，10 月 1 日为 150，10 月 2 日为 -30；截至截止时点的订单批次净额为 120。不要把跨日退款直接改写成原支付日退款而不说明回溯规则。

在基础案例通过后，每次只改变一个条件，至少完成下面 8 项并用查询结果断言：

- 重复支付回调：同一事件 ID 重放后金额不变。
- 失败支付：有金额但状态失败，不纳入成功支付金额。
- 无退款订单：左关联后仍保留，退款为 0。
- 截止时点边界：等于截止时点的事件排除，之前的纳入。
- 零分母：没有成功支付订单时约定返回 NULL，而不是报错。
- 迟到退款：区分事件时间和入仓时间，说明何时重算历史结果。
- 客户 SCD2：有效期采用左闭右开；边界上的交易只能匹配一个版本。
- 不同组大小下的比率汇总：重新汇总分子/分母，与直接平均比率对比。

每个断言写明输入变化、预期值、实际值和结论。先在 SQLite（金额用整数分）或本地 DuckDB（DECIMAL）中选一个执行，不引入湖仓集群作为前置条件。三类事实表先完成设计比较，只实现支付/退款事务事实和指标所需最小视图即可。

## 3. 从规范到可校验模型

阅读顺序：

1. `README.md`：项目边界与模型交换目标。
2. `core-spec/spec.md`：datasets → fields → relationships → metrics → 名称解析。
3. `core-spec/ossie-schema.json`：必填项、类型、嵌套结构。
4. `examples/tpcds_semantic_model.yaml`：抽取一个销售事实和客户/商品/日期维度，逐项解释。
5. `core-spec/relational_semantics.md`、`core-spec/expression_language.md`：关系与计算规则，不把格式声明当查询执行承诺。
6. `validation/validate.py` 与相应测试：追 `main → validate_file → validate_document`，再按该 commit 实际调用定位检查函数，记录文件与行号。

环境准备：核心验证脚本声明 Python >=3.11；在独立实验虚拟环境中按脚本声明安装 pyyaml、jsonschema、sqlglot，记录实际解析后的依赖版本。完整环境和运行日志放在 scratch 根目录下，不写入上游源码目录。

```powershell
# 当前目录为锁定 commit 的 Ossie checkout；$studyPython 为实验虚拟环境的 python 路径
& $studyPython validation/validate.py examples/tpcds_semantic_model.yaml
& $studyPython validation/validate.py 'D:\hy\读书笔记\AI读源码\04-笔记\贯穿案例\实验\订单支付退款.semantic.yaml'
```

需要负向验证：错误类型、重复名字、字段引用不存在等案例能被检测；“数据中的重复支付事件”则由第 2 周建立的 SQL 断言检测，不交给 Schema 校验。

实现提醒：该锁定版本的指标引用声明字段，不能直接引用其他指标。必要时先在 SQL 视图中形成经过验证的字段/公共粒度，再建立语义映射。模型中的 description 与 ai_context 必须来自已明确的合同。

## 4. 转换与 AI 对照实验

### 转换实验

- 选择与你现有工具接近的一个转换器（优先 dbt；没有对应环境时选择能本地生成文件的转换路径，按其 README 确认方向与依赖）。
- 转换器固定到版本锁定表的 commit，其 ossie 子模块保持该仓库记录的 commit。它与第 6 周使用的核心版本不同，先比较 Schema；必要时显式迁移副本，保留迁移记录。
- 正向导出、再导回，逐项比较主键、字段类型、表达式、关系、description、ai_context、custom_extensions。
- 转换器不支持双向时，记录限制并增加一个支持所需方向的转换器，完成一次真实往返；不得用手工重写冒充往返。
- 用同一份测试数据和指标合同验证转换后的结果；只有文件生成且未运行目标查询时，明确标为“结构验证，执行未验证”。

### AI 上下文实验

- A 组：只有相同数据源的表结构。
- B 组：同一表结构，加已验证的业务定义、关系说明、指标口径、时间边界和同义词。
- 固定模型版本、参数、数据快照、问题顺序与工具权限。第 9 周执行 10 题 × 2 组 × 1 次，共 20 次，记录 SQL、结果和错误归因；第 22 周在最新数据快照重跑同一题集。时间允许时各补到 3 次以观察一致性，这部分列为选修。小样本用于学习诊断。
- 10 题至少覆盖：支付总额、退款总额、净支付、成功支付订单数、每订单净额、退款金额率、订单退款占比、跨日退款、商品分摊歧义、客户历史属性。
- 按结果数值、过滤状态、时间口径、关联粒度、无法回答时是否澄清逐项评分，比较通过率和重复运行的一致性，不以 SQL 看起来合理作为正确标准。
- 优先使用锁定的 Datus；先核对是否有 Ossie 原生接入。没有则将模型整理成其支持的上下文格式，记录适配路径；Ossie 不是模型执行引擎，也不保证能被任意 Agent 自动读取。

## 5. 验收清单

- 能闭卷画出“业务过程 → 事实与维度 → 指标 → Ossie → BI/AI”的链路，并解释各层职责。
- 至少 5 个指标合同完整，基础案例及 8 项边界 SQL 验证通过。
- 至少一份自建模型通过锁定版本校验，负向案例有效；验证记录附命令、版本、日期和结果。
- 有一次真实模型往返的差异报告；未执行验证的部分有明确状态。
- 有 10 题的 AI 对照记录和错误归因，能提出至少一个可迁移到工作的改进建议。
- 笔记中的规范结论有锁定源码位置；未运行部分标记“待验证”，完成后再更新 `04-笔记/README.md`。

需要压缩时按总计划缩减选修内容，保留粒度、指标合同和 SQL 对账。Ossie 全仓通读不作为完成条件。
