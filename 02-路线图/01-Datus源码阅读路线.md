# Datus 源码阅读路线（3 周）

> 状态：旧版固定周次资料，现仅按需参考。文中的“第 N 周”、必交产出和统一排期不再是当前任务；请以 [AI Agent 学习主线](../02-路线图/00-总路线图.md) 为准。

> Datus 是开源的「数据工程 Agent」，定位是让 AI 直接和数据库/数仓对话、生成并执行 SQL、沉淀数据上下文。
> 版本锚定：`v0.4.3`（2026-10-15 发布，见 `00-版本锁定.md`）。
> 仓库具体布局会随版本变化，**本路线中的所有结构描述都需要你在 Stage 0 用 P1 提示词重新核对一遍**，核对结果直接覆盖本文件末尾的「仓库地图」小节。

> 统一排期：第 7–9 周；输入是第 2 周的 SQL 基线、第 5 周 demo 与第 6 周 Ossie 模型。全部排期见 [总学习计划](00-总路线图.md)。

## 为什么在框架与语义模型之后学习

- 和你的工作重叠度最高：你既做数据平台，又在学 Agent，Datus 正好是两者的交叉点。
- Python 代码量小，3 周能读完主干。
- 已完成统一计划第 3–5 周（LangChain/LangGraph 巩固），你手上有 `mini_graph` 和 Pregel 的理解，读 Datus 时每个设计都能立刻找到对照物：「这里是状态机还是自研循环」「它的持久化和 checkpointer 差在哪」。**这个对照，就是这一阶段最大的收获。**

## 前置知识

- 统一计划第 3–5 周全部完成，尤其是 LangGraph 运行时那一周：说得清超步、reducer、checkpointer、interrupt。
- 自己的 `mini_graph.py` 还在，随时能翻。
- 一点 Text2SQL 的常识（schema 检索、few-shot、执行反馈重试）。
- 不需要懂 Flink/Paimon。

## Stage 0：跑通（第 7 周前半）

不跑通不读代码。

1. 克隆仓库，按版本锁定表切换到 v0.4.3，记录 commit。
2. 按 README 安装（大概率是 `pip install -e .` 或 `uv sync`），准备一个本地 DuckDB 或 SQLite 数据源。
3. 跑一次完整的交互：提问 → 生成 SQL → 执行 → 返回结果。**把每一步的日志留下来**。
4. 用 P1 生成 `CLAUDE.md` 仓库地图，抽查 3 处行号。
5. 用 P7 搞清楚「`datus` 命令的入口函数在哪」。

验收：能用一条命令启动，用自然语言问出一个 SQL 答案，并且知道这个回答经过了哪几个模块（哪怕只是名字）。

## Stage 1：主链路（第 7 周后半至第 8 周）

**唯一目标：把「用户一句话 → 最终答案」这条链路走通，每跳留行号。**

按这个顺序追，不要跳：

1. **入口层**：CLI / API 入口 → 会话初始化（加载配置、连接数据源、加载上下文）。
2. **Agent 循环**：一次用户输入如何进入循环？循环的终止条件是什么？最多几轮？
3. **上下文组装**：这一轮送给 LLM 的 prompt 里到底有什么？schema、指标、历史 SQL、工具描述分别从哪来、怎么排序、怎么裁剪？
4. **工具调用**：模型返回工具调用后，谁负责分发？工具注册表长什么样？SQL 执行工具怎么连数据库、怎么处理超时和错误？
5. **结果回写**：执行结果如何回到模型、如何形成最终回答、如何持久化到会话历史。

每追完一跳，填进笔记模板的链路表。追完后画时序图，标注哪些步骤是同步、哪些是流式。

**关键问题**（这一周必须回答的）：

- 它用的是自己的 agent loop，还是 LangGraph/LangChain？为什么？
- 工具是怎么注册的？加一个新工具要改几个文件？
- 上下文有没有预算控制？超长时怎么截断？
- LLM 调用失败/超时/返回非法 JSON 时怎么处理？

## Stage 2：语义验证与选读（第 9 周）

按第 9 周任务精读 context，并从工具层/subagent 选一个；其余专题保留为后续参考，笔记合并为一份语义验证报告。

**专题 1：Context Engineering（最重要）**
Datus 的核心卖点大概率就在这里。要搞清楚：数据上下文（表结构、字段描述、指标定义、示例 SQL、业务语义）以什么形式存储、怎么检索（向量？关键词？还是结构化索引？）、怎么注入 prompt、怎么随会话演进。这是你能直接搬回工作的部分——你们内部的 Text2SQL 大概率卡在上下文上。

第 9 周整合练习：按 [实践指南](05-数据建模与Ossie实践指南.md) 复用已有模型与题集，完成一次模型往返和「仅表结构 / 补充语义」上下文对照。先核对 Ossie 原生接入能力；本周精读 context 与工具层/subagent 中的一个，其余专题按需选读。

**专题 2：Subagent 编排**
有没有多个角色（如「调研 agent」「SQL agent」「校验 agent」）？它们之间怎么交接？是串行、并行还是路由？和 LangGraph 的 supervisor 模式比，差别在哪、为什么。

**专题 3：工具与数据源适配层**
数据库适配器怎么抽象？支持哪些方言？方言差异（分页、函数、日期）在哪一层处理？加一个新数据库要做什么。

**专题 4：质量保障**
有没有 SQL 校验、执行前 dry-run、结果自检、重试、评估集？这部分往往最粗糙，也最能体现工程成熟度——读它是为了知道「做一个能上生产的 Agent 还缺什么」。

**专题 5（可选）：MCP / 外部集成**
如果版本支持 MCP，看它作为 client 怎么接外部工具，和你们未来可能的集成方案对照。

## AI 提示词（针对 Datus）

- P2 场景：`入口是 <cli 入口函数>，追踪「用户提问：<问题>」这一次请求的完整路径，直到返回答案。`
- P3 场景：`请解释 context 的构建流程：从会话开始到拼出 prompt，涉及哪些数据源、如何筛选和排序。`
- P4 场景：`对比 Datus 的 agent loop 和 LangGraph 的 StateGraph 在 <状态/中断/重试> 上的差异。`
- P8 场景：`设计一个最小实验：给 Datus 接一个本地 duckdb，验证 <schema 检索> 是否真的生效（比如加一个无关表看它会不会被注入）。`

## 验收问题（能答 80% 算过）

1. 一条用户请求从进来到返回，经过了哪些模块？画出时序图。
2. 送给 LLM 的 prompt 由哪几部分组成？各部分从哪来？
3. 工具调用的完整生命周期是什么？失败怎么处理？
4. 会话状态存在哪？重启后还在吗？
5. 加一个新的数据源需要改哪些地方？
6. 它的上下文检索是语义检索还是结构化检索？为什么这么选？
7. 它为什么没有直接用 LangGraph？如果换成 LangGraph 实现，哪些能力能白拿（超步、checkpoint、中断），哪些拿不到或更难做？
8. 如果要把它接到公司内部数仓，最大的三个障碍是什么？

## 常见坑

- 不要把时间花在 UI / 前端上，除非你的工作要做产品化。
- Python 项目的「实现」往往很薄，价值在 prompt 和数据结构里，读的时候多看 prompt 模板和配置。
- 版本迭代快，网上博客大概率过期，一切以你 checkout 的代码为准。
