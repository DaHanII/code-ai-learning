## 为什么是这个顺序

1. **LangChain / LangGraph（3 周）**——你的基础只到「跑通 demo」，缺的是抽象层和运行时。而 LangGraph 1.0 本身就是一个设计精良的小型分布式执行引擎（超步、状态合并、checkpoint），读它的源码难度正好，收益直接作用于后面三个项目。
2. **Datus（3 周）**——和你的工作直接重叠，Python 代码量小。刚补完 LangGraph，正好带着「如果是我会怎么设计」的眼光去读，对比最有价值。
3. **Paimon（5 周）**——你天天在用，代码规模适中、数据结构清晰。Paimon 的 snapshot 和 Flink 的 checkpoint 是同一类「一致性快照」问题，先读它能给 Flink 铺路。
4. **Flink（5-6 周）**——最大的坑，放后面是因为它需要前面积累的耐心和方法。
5. **Spark（1-2 周）**——工作中够用即可，只有做查询优化才深挖 Catalyst。

> 如果工作里有紧急的 Flink 问题，允许插队：临时按 `03-Flink源码阅读路线.md` 的 Stage 1-2 读两周，处理完再回到主线。项目驱动意味着顺序可变，但每个项目都必须走完 L1 骨架层。

## 时间不够时的最小版本

只投入一半时间时，按这个顺序砍：

- **阶段 0 压到 2 周**：跳过 Stage 3 的评估与成本优化，只保留可观测和健壮性；mini_graph 只做节点、边、内存 checkpointer。
- Datus 的 MCP / 前端不读。
- Paimon 的 Spark 集成、z-order 细节不读。
- Flink 的 HA、Metrics、REST 不读。
- Spark 只读 Stage 1。

**不能砍的**：阶段 0 的第 2 周（Pregel 运行时）、每个项目的 L1 主链路、Paimon 的 commit、Flink 的 checkpoint、每篇笔记的「对工作的启发」。

## 每个阶段的完成标准（硬指标）

一个阶段算「读过」而不是「看过」，需要同时满足：

1. 有可运行的产出（阶段 0 是两个 mini 框架 + 一个 demo；其余项目是仓库地图 + 笔记）；
2. 笔记都标「已验证」，链路表每一行都有 `文件:行号`；
3. 能不看资料画出主链路时序图；
4. 能答出对应路线文档「验收问题」中的 80%；
5. 至少有一篇笔记的「对工作的启发」在工作里被用过（改一个配置也算）。

## 和现有学习的关系

`Langchain1.0-Langgraph1.0-Learning-main` 那套仓库从「素材」变成「考卷」：不再从头看一遍，而是关掉它自己重写练习，再打开对照。会做但写不出的地方，才是你真正要补的地方。

阶段 0 结束后，建议在那边仓库补一个 `phase5_source_reading/` 目录，放 `mini_chain.py`、`mini_graph.py` 和对比笔记——那套仓库是你的实践区，这套 `AI读源码` 是方法论和路线区，两边互相引用即可。

`精益数据分析`、`博弈论` 那些笔记属于另一条线，不受影响。
