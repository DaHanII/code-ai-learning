# 数据建模与 AI 数据工程统一学习计划

> 唯一排期入口：全部内容按下面第 1–22 周连续推进。各项目文档提供具体阅读与练习，章节序号表示材料分类。
> 默认投入：每周约 8 小时，共约 176 小时；预计 22 周。按实际开始时间执行，不预设日历日期；验收未过则顺延。
> 贯穿目标：从业务需求设计可信的数据模型，让 AI 正确使用，再解释数据如何被存储、流式更新和跨引擎查询。
> 版本统一见 [版本锁定](00-版本锁定.md)，本次调整于 2026-10-26。

## 1. 一条主线与阶段衔接

**业务与维度模型 → Agent 框架基础 → Ossie 语义表达 → Datus 数据问答 → Paimon 湖表 → Flink 实时计算 → Spark 对账与闭环。**

先明确业务对象、粒度和指标，后面才有标准答案；先掌握 LangGraph 运行时，再判断 Datus 的设计；先理解 Paimon 提交与快照，再追 Flink checkpoint。最后由 Spark 对账检验存储、计算和语义层的结果是否一致。

Ossie 在第 6 周表达第 1–2 周的建模结果，第 9 周作为 Datus 上下文与转换实验的输入，在后续存储和计算阶段持续修订。AI 评估题集沿用同一组业务问题。

## 3. 贯穿案例与成果复用

全程使用“订单—支付—退款—客户—商品”。第 2 周冻结一个合成基线数据集，订单批次、成功状态、时区、截止时点和去重规则均写入合同；标准数据和边界见 [实践指南](05-数据建模与Ossie实践指南.md)。

- 第 1–2 周设计业务、逻辑和维度模型，建立 SQL 标准答案。
- 第 3–5 周复用这些 SQL 构造工具与 demo，形成统一题集。
- 第 6–9 周把同一模型表达为 Ossie，并检验 Datus 的业务理解与转换损失。
- 第 10–14 周把同一事实/维度迁移到 Paimon，保留数据版本和 snapshot。
- 第 15–20 周引入更新、迟到和失败恢复，用原断言检查业务结果。
- 第 21–22 周由 Spark 读取同一湖表，与实时结果和语义层完成对账。

业务术语、指标合同、样例数据、语义模型、题集持续复用；物理 source、更新策略或口径变化时记录版本及变更理由，重新运行受影响的断言。

## 4. 每周执行方式与阶段验收

每周约 8 小时：概念与规范 2 小时，追源码/画图 2 小时，实验与对账 3 小时，闭卷复述和整理 1 小时。实践指南中的练习按对应周拆解执行；未完成则顺延，不在同一预算内追加另一条路线。

验收贯穿每周：

1. 本周产出存在，记录环境、版本、输入、命令与实际结果；未运行的部分标记“待验证”。
2. 业务与指标问题用数据和 SQL 断言验收；规范/源码结论附固定 commit 与文件位置。
3. 不看资料能解释本周主链路，答出项目指南中适用问题的 80%。
4. 第 2、6、9、14、20、22 周核对阶段成果：模型合同 → 语义表达 → Agent 消费 → 湖表落地 → 实时更新 → 跨引擎闭环。没有通过就先修正。
5. 结果比较固定数据版本和时点。Ossie 文档校验、转换结构验证、目标系统执行验证分别记录。

## 5. 时间不足时怎样取舍

先缩减选修：多转换器、ontology/SDK、Datus MCP/前端、多 subagent、Paimon 多专题、Flink 多方向深挖、Spark Catalyst 扩展与 AQE 专题。第 9 周题集先各跑一次，重复评估列为选修。

保留：粒度与指标合同、SQL 基线与边界断言、LangGraph 运行时、Ossie 校验、Datus 一问一答、Paimon commit、Flink checkpoint、最终跨引擎对账。每周只有约 4 小时时，按同一顺序将时间拉长至约 44 周，不另建并行计划。

工作问题允许临时插队；处理后回到当前周，更新完成记录。知识框架用于查漏，项目指南用于深入，全局排期只维护本文件。
