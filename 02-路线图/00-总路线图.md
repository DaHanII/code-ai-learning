# AI Agent 学习主线：用现有项目理解机制

> 2026-10-26 修订。主目标是学习 AI Agent 的原理与工程能力；`data-employee` 等现有实践是练习场，Themis 的语义层工作只用于帮助理解 Ossie。取消原 22 周固定排期和额外的全栈造轮子任务。
> 建议每周额外投入 2–3 小时。实际开发、排障、评审中完成了同等验证，就直接计入，不再重复做一遍。忙时按学习卡顺延。

## 1. 要学会什么

按一条 AI 请求的真实流转组织知识：

**用户输入 → 模型与工具描述 → Agent 决策 / 状态 → 工具执行 → 证据回填 → 上下文管理 → 最终回答 → 评估与恢复。**

终点不是看完某个仓库，而是能独立解释和改进一个 Agent：它为什么调用这个工具、用了哪些上下文、哪些事实支撑回答、失败后如何继续、怎样知道改动让效果变好。

现有 `D:\hy\project\data\data-employee` 使用 LangChain `create_agent`，有业务工具、执行记录、上下文和服务恢复能力；它是首选练习场，不需要另做一套 mini_chain、mini_graph 或独立 Agent demo。已有 `Langchain1.0-Langgraph1.0-Learning-main` 只在概念卡住时查例子。

## 2. 学习顺序：六张卡，不按项目堆课

| 学习卡 | 只回答的核心问题 | 用现有实践做什么 | 完成证据 |
| --- | --- | --- | --- |
| A. Agent 调用链 | 一次提问怎样变成模型调用、工具调用和最终回答？ | 跑一个脱敏/演示问题，对照 `investigation/agent.py`、`registry.py` 与执行记录 | 一页调用链，指出实际输入、ToolMessage 和停止条件 |
| B. 状态与恢复 | 工具结果与会话状态存哪，失败后从哪里继续？ | 选现有检查点或恢复场景，追一条真实路径 | 说清状态边界、可能重做的外部操作和一个验证结果 |
| C. 上下文与证据 | 模型到底看到了什么，什么被裁剪，什么仍可核验？ | 对比一次模型输入与完整工具证据，观察长结果处理 | 一张“模型可见 / 证据留存”对照表和一个可能失真的例子 |
| D. 质量与评估 | 如何区分工具错误、推理错误、口径错误和证据不足？ | 从现有业务问法挑 3–5 条，固定输入、预期行为、结果与错因 | 小型回归表；改动前后能复查 |
| E. 对照读 Datus | 另一个数据 Agent 怎样组织上下文、工具和循环？ | 只追 Datus 的一问一答主链路，与自己的 Agent 对比一个设计问题 | 一条带源码位置的差异及是否值得借鉴的结论 |
| F. Ossie 初探（支线） | 语义模型交换格式能表达什么，不能保证什么？ | 读 README、核心规范和一个示例；将 Themis 的一个**脱敏**概念映射到 dataset / field / relationship / metric | 一页概念映射和边界说明；不要求接入或转换 |

**主线优先级：A → B/C → D → E。** B 和 C 可随当前工作交换。F 只安排一次约 1–2 小时的了解；Themis 的语义层建设继续按工作计划推进，不占用 AI 学习主线。若当前 Agent 暂未碰到某种机制，用现有测试或文档验证即可，不为学习强行开发功能。

## 3. 前两次怎么开始

### 第一次：看清一次 Agent 请求（约 2 小时）

1. 在 `data-employee` 选择一个已有的演示/脱敏问题，使用项目现有运行方式和记录；不为了学习发起不必要的生产调用。
2. 从记录中找出用户输入、一次模型的工具调用、工具参数、工具结果、最终回答与停止原因。
3. 只打开 `investigation/agent.py`、`investigation/registry.py` 及实际命中的一个工具；画 6–8 个节点的调用链。
4. 不看资料回答：`create_agent` 管什么，本项目的 middleware/业务工具管什么？回答依据来自哪条工具结果？

产出可以是一页笔记或现有代码评审说明。看懂真实调用链就算完成，不要求重写框架。

### 第二次：选一个看不懂的机制（约 2–3 小时）

从**状态恢复**和**长结果上下文**二选一，优先选近期工作实际碰到的：

- 状态恢复：找一次中断与恢复的记录或现有测试，弄清“保存了什么、恢复时重放什么、哪类外部查询可能再执行”。必要时再查 LangGraph/checkpointer 对应实现。
- 长结果上下文：找一次大结果返回，比较模型可见摘要、完整证据及最终回答，判断裁剪是否导致丢失关键事实。必要时再读上下文管理资料。

只研究选中的一条机制，留下一个可以复核的例子和结论。另一条留到下一次。

## 4. 源码怎样读才不增加无谓工作

先从运行记录或测试确定真实行为，再读**一条**调用链上最关键的函数。遇到框架边界才跳到 LangChain/LangGraph 的对应版本源码；每次只回答一个问题，例如“工具结果何时写入消息状态”或“恢复时哪些节点会重新运行”。AI 可以帮定位和质疑，结论以本地代码、测试及运行记录核实。版本见[版本锁定](00-版本锁定.md)，但先核对当前项目实际安装版本，不为学习升级工作环境。

Datus 是对照样本，不要求整仓阅读。Paimon、Flink、Spark 是数据系统专题，当前**不列入 AI 主线**；将来出现相关工作问题再使用旧指南。也不要求 LangSmith 远端 tracing：项目已有本地执行记录，先用现有证据。

## 5. Ossie 的边界

Themis 正在构建语义层，因此了解 Ossie 有价值，但只需要辨认：它如何描述数据集、字段、关系、指标和上下文；哪些业务约束仍需要 Themis 自己实现和验证。格式通过校验不等于数据、指标或 AI 回答正确。

一次 1–2 小时的阅读和概念映射就够。**不要求**现在做订单合成数据、完整维度建模课程、Ossie YAML 落地、转换器往返或 Datus 接入。只有工作明确需要模型交换时，再从[实践指南](05-数据建模与Ossie实践指南.md)挑相应部分。
